1.Overview & scope

TechSmith (offline POS/ERP) is being integrated with Zopping as a channel plugin so both sides share one catalog, one stock pool, one customer base and one order pipeline. Four flows are in scope:

TechSmith → Zopping

Product master

Create new products, update existing ones, toggle active/inactive.

TechSmith → Zopping

Inventory

Push stock and price on a fixed interval.

TechSmith → Zopping

Customer

Create/update customers registered offline.

Zopping ↔ TechSmith

Orders

Zopping pushes online orders to TechSmith; TechSmith reserves stock, packs, invoices; Zopping owns delivery and returns and reports status back.

2.Integration architecture

One Platform API, backend gateway zopping.com/api/<service>/<resource>, authenticated by partner token, scoped to organizationId (+ storeId). TechSmith calls it directly for product/inventory/customer; for orders the direction reverses — Zopping pushes orders out, TechSmith pushes pack/invoice status back.

3.Authentication & environment

  • Credential: partner Developer Token — Authorization: Bearer $ZOPPING_TOKEN on every call.
  • Scope: every request carries organizationId, plus storeId where store-scoped.
  • RBAC: endpoints need explicit grant to TechSmith's token — confirm during onboarding.
  • Environments: confirm sandbox vs. production credentials separately.

4.Extensions required

Zopping ships many capabilities as per-organization extensions that gate whether an endpoint or field behaves as expected. Zopping's team installs and manages these for the org as part of onboarding — no setup action needed on TechSmith's side.

For reference, this integration touches: MultiStoreSupport, MultiVariantSupport, EntityMetaData, OrderReturns, DeliverySlots/DeliveryAreaSupport, OnlinePaymentSupport. TechSmith can verify current status anytime with GET /api/account-service/extension?organizationId=<org-id>&status=ENABLED.

5.Product master sync

TechSmith → Zopping. TechSmith creates and updates products; active/inactive is a status change (ENABLED/HIDDEN), not a delete. Look up by clientItemId before writing — never re-POST the same SKU.

6.Inventory sync (stock & price)

TechSmith → Zopping, on an interval. Price/stock are per-store, on an item (productId + storeId) — always via the Inventory API, never Catalog. Use stockDelta when TechSmith only knows the change, not the absolute count.

8.Order fulfillment lifecycle

The core bidirectional flow: an online order lives in Zopping; TechSmith reserves stock, picks, packs and invoices it; Zopping then owns delivery and reports status back throughout.

sequenceDiagram
  participant Cu as 🧑 Online Customer
  participant Z as 🛒 Zopping (Order Service)
  participant L as 🚚 Zopping Logistics / 3PL
  participant T as 🏬 TechSmith

  rect rgb(232, 241, 252)
  Cu->>Z: Checkout / place order
  Z-->>Z: 🔔 ORDER_CREATE fires
  Z->>T: Push order (event integration) — items, amount, address, slot
  Note over T: (backstop) GET /order-service/order?status=CONFIRMED
  end

  rect rgb(234, 246, 227)
  T-->>T: 🔒 Reserve stock — block offline sale of these units
  T-->>T: 📦 Pick & pack, generate invoice
  T->>Z: PUT /order-service/order/{id} {status: PACKED}
  T->>Z: 🧾 Share invoice reference (mechanism: open item)
  Z-->>T: ✅ 200 OK
  end

  rect rgb(255, 244, 214)
  Z->>L: Hand off packed order (courier eligibility + dispatch, or own-fleet trip)
  L-->>Z: 🚚 ORDER_DISPATCH
  Z-->>T: 🔔 ORDER_STATUS_UPDATE (DISPATCHED)
  L-->>Z: 🏠 ORDER_COMPLETE
  Z-->>T: 🔔 ORDER_STATUS_UPDATE (DELIVERED)
  end

9.Returns & reverse logistics

Zopping-owned, status shared with TechSmith. Zopping arranges the reverse pickup and keeps TechSmith informed so stock can be reconciled once it's physically back.

10.Event catalog & webhook subscription

Push, not poll: subscribe once via POST /api/partner-integrations/event-integrations and react as events fire; keep a low-frequency poll only as a backstop. Zopping must provision a delivery template pointed at TechSmith's webhook.

DomainEvents
OrdersORDER_CREATE, ORDER_STATUS_UPDATE, ORDER_PACK, ORDER_DISPATCH, ORDER_COMPLETE, ORDER_CANCEL
InventoryINVENTORY_UPDATE
CustomersCUSTOMER_CREATE, CUSTOMER_BASIC_EDIT
ProductsPRODUCT_CREATE, PRODUCT_UPDATE, PRODUCT_DELETE

11.Idempotency & error handling

  • Map ids, don't mirror them — clientId/clientItemId on products/customers, referenceNumber on orders. Look up, then PUT; never re-POST.
  • Dedupe events on event id / referenceNumber — treat redelivery as a no-op.
  • Statuses are forward-only — don't move an order backwards from TechSmith's side.
  • Reconcile inventory periodically against /inventory-service/inventory-log to catch drift.

12.Open items to confirm with Zopping

  1. Invoice hand-off — how TechSmith's own invoice (number/URL/PDF) reaches Zopping; likely metaData, not yet a first-class field.
  2. Ingestion surface — direct Catalog/Customer APIs, or a named partner-connector under /api/partner-integrations/…?
  3. Event template — Zopping needs to provision delivery to TechSmith's webhook before go-live.
  4. Offline stock reservation — purely internal to TechSmith, or reflected back as a Zopping-side hold?
  5. Extensions & environments — confirm what's enabled for the org, plus sandbox access and rate limits.
